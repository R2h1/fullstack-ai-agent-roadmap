# W08 - 模块系统与工程化 📦

> 💡 **本周目标**：把零散的 JS 文件组织成可维护、可发布、可复用的工程。从"写脚本"升级到"做项目"。

## 🕰️ 一、模块的"进化史"

> 📖 **类比**：从一个人在一张纸上乱写（全局变量），到大家用 USB 互传文件（IIFE），到云盘共享（CommonJS），最后到现代浏览器/Node 都认的"国际标准"（ESM）。

| 时代 | 方案 | 特点 |
|---|---|---|
| 远古 | 全局变量 | 命名冲突地狱 |
| 2010 | IIFE | 立即执行函数，闭包隔离 |
| 2011 | AMD（RequireJS）| 浏览器异步加载 |
| 2012 | CMD（SeaJS）| 阿里玉伯出品 |
| 2009 | CommonJS | Node.js 同步加载 |
| 2014 | UMD | 一份代码兼容多种 |
| 2015 | **ESM** | 官方标准，浏览器/Node 通用 |

## 📜 二、CommonJS（Node.js 经典）

```javascript
// math.js
function add(a, b) { return a + b; }
module.exports = { add };
// 或：exports.add = add;

// app.js
const { add } = require('./math');
console.log(add(1, 2));
```

> ⚠️ `exports` 只是 `module.exports` 的别名引用。如果直接 `exports = {...}` 会断开关系，导出的依然是原对象。**记住：永远赋值给 `module.exports`**。

特点：

- **同步加载**（require 立即返回）
- 值是**拷贝**（导出基本类型后改不会影响）
- 可以**条件 require**

## 🌐 三、ESM（现代标准）

```javascript
// math.js

// 命名导出：可以导出多个，名字就是变量名
export function add(a, b) { return a + b; }
export const PI = 3.14;

// 默认导出：一个模块「只能有一个」，import 时名字随便起
export default class Math2 {}


// app.js

// 混合导入：默认导出在前（名字任意），命名导出用 {} 精确匹配
import Math2, { add, PI } from './math.js';

// 命名空间导入：把「所有命名导出」收集成一个对象
// ⚠️ default 也在里面，访问方式是 math.default，不是 math.Math2
import * as math from './math.js';

// 重命名：解决命名冲突，或让名字更贴业务
import { add as plus } from './math.js';

// 动态导入：返回 Promise，可以条件加载、按需加载
const m = await import('./math.js');
// ⚠️ 顶层 await 要求「当前文件本身是 ES Module」——
//    .mjs 扩展名，或 package.json 里 "type": "module"
```

### CJS vs ESM 关键差异

| 维度                     | CommonJS         | ESM                    |
| ---------------------- | ---------------- | ---------------------- |
| 加载                     | 同步               | 异步（动态时）                |
| 值                      | 拷贝               | **绑定**（引用）             |
| `this`                 | `module.exports` | `undefined`            |
| `__filename/__dirname` | 有                | 无（用 `import.meta.url`） |
| top-level await        | 不支持              | ✅                      |
| Tree shaking           | 难                | ✅ 静态分析友好               |

### 互操作（最容易踩坑的地方）

```javascript
// ============================================================
// CJS 引 ESM
// ============================================================
// 动态 import() 返回 Promise，所以通常要 await；
// 但 CJS 没有顶层 await，不能直接写在 .cjs 最外层，
// 必须放在 async 函数或 async IIFE 里。
//
// 版本说明：
// - await import(esm)：所有支持 ESM 的 Node.js 版本都可用。
// - require(esm)：Node.js v20.19.0 / v22.12.0 起默认启用；
//   v24.15.0 起标记为 stable。
//   前提：目标 ESM 及其依赖图中不能有顶层 await，
//   否则 require() 会抛 ERR_REQUIRE_ASYNC_MODULE。
(async () => {
  const esm = await import('./esm-only.mjs');
  // esm.default 对应 ESM 的 default export；
  // ESM 的具名导出在 esm.xxx 上。
  // const { foo } = esm;
})();

// ============================================================
// ESM 引 CJS
// ============================================================
// 默认导入拿到的是 CJS 的 module.exports 整体。
// 这个行为从 Node.js 支持 ESM 起就存在，没有特殊版本门槛。
import pkg from 'lodash'; // 约等于 CJS: const pkg = require('lodash')
const { debounce } = pkg; // 从 module.exports 对象上解构
// 备选：具名导入依赖 Node.js 对 CJS 的静态分析（cjs-module-lexer）。
// 只有能被静态识别的导出写法才可靠，例如 exports.xxx、
// module.exports = { xxx } 等。
// lodash 这类 UMD/动态挂载的包不保证支持具名导入；
// 失败时请用上面的 default import 解构方式。
//
// 注意：下面这行和上面的 const { debounce } = pkg; 二选一，
// 同时启用会重复声明 debounce。
//
// import { debounce } from 'lodash';
```

> 💡 **package.json 怎么标识**：`"type": "module"` 让 `.js` 视为 ESM；不加默认 CJS。`.mjs` 强制 ESM；`.cjs` 强制 CJS。

## 🌳 四、Tree Shaking（摇掉死代码）

```javascript
// utils.js
export const used = () => 1;
export const unused = () => 2;

// app.js
import { used } from './utils.js';
console.log(used());
```

构建工具（Vite/Rollup/webpack 5）会**静态分析**，把 `unused` 从最终 bundle 删掉。

**前提**：

1. 用 ESM（CJS 是动态的，分析不了）
2. 没有副作用，或在 `package.json` 标 `"sideEffects": false`

## 📋 六、package.json 全字段

```json
{
  "name": "my-pkg",
  "version": "1.2.3",          // semver: 主版本.次.补丁
  "type": "module",             // 文件默认 ESM
  "main": "./dist/index.cjs",  // CJS 入口（老）
  "module": "./dist/index.mjs",// ESM 入口（webpack 用）
  "types": "./dist/index.d.ts",
  "exports": {                  // 现代多入口（最重要！）
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs"
    },
    "./utils": "./dist/utils.mjs"
  },
  "files": ["dist"],            // 发布到 npm 的文件
  "scripts": {
    "build": "tsup",
    "test": "vitest"
  },
  "dependencies": {},
  "devDependencies": {},
  "peerDependencies": {},
  "sideEffects": false          // 帮助 tree-shaking
}
```

### semver 语义化版本

```
1.2.3
│ │ └── patch：bugfix
│ └──── minor：新增功能（兼容）
└────── major：破坏性更新

^1.2.3 → 兼容更新（1.x.x 内最新）
~1.2.3 → 仅 patch（1.2.x）
1.2.3  → 锁死
```

### 锁文件作用

`package-lock.json` / `pnpm-lock.yaml` 记录**精确版本 + 依赖树**，保证团队和服务器装出一样的包。**必须提交到 git**。

## 🔧 九、手写 mini require（CJS 简化版）

```javascript
const fs = require('fs');
const path = require('path');
const vm = require('vm');

const cache = {};

function myRequire(filePath) {
  const abs = path.resolve(filePath);
  // path.resolve 把「相对路径」转成「绝对路径」——
  // 缓存键必须用绝对路径，否则 './a' 和 '../dir/a' 会命中不同的缓存项。

  if (cache[abs]) return cache[abs].exports;
  // 命中缓存：返回的是「当前的 module.exports」。
  // 注意不是 cache[abs] 本身 —— 模块可能把 module.exports 重新赋值过。

  const module = { exports: {} };
  cache[abs] = module;  // ← 先放进缓存解决循环依赖
  // 关键顺序：在「执行模块代码」之前就放入缓存。
  // A require B、B require A 时，B 拿到的 A 是「已缓存但未执行完」的半成品 ——
  // 这正是 CJS 循环依赖「拿到部分导出」的来源。

  const code = fs.readFileSync(abs, 'utf8');

  const wrapper = `(function(exports, require, module, __filename, __dirname) { ${code} })`;
  // 这就是 Node 隐式做的事：把模块代码包进一个函数，
  // 五个参数正是前面说的「exports / require / module / __filename / __dirname」。
  // 为什么需要 wrapper？模块代码里的顶层 var/function 应该只属于这个模块，
  // 不能泄漏到全局 —— 函数作用域提供了隔离。

  const fn = vm.runInThisContext(wrapper);
  // runInThisContext 编译但不执行 —— 返回一个函数对象。
  // 不用 eval / new Function 的原因：`eval` 会「看到」`myRequire` 里的局部变量（`abs`、`module`、`cache`）——模块代码能意外访问加载器的内部状态。`runInThisContext` 编译出的函数只认「调用时传进去的参数」，隔离更彻底。。

  fn(module.exports, myRequire, module, abs, path.dirname(abs));
  // 调用 wrapper，传入五个参数。
  // ⚠️ 注意传的是 module.exports 的「当前值」——
  //    如果模块内部执行 exports = {...}，形参 exports 指向新对象，
  //    但 module.exports 没变，所以最终返回的还是原对象。这就是前面讲的「断链」。

  return module.exports;
  // 返回的是「执行完之后」的 module.exports ——
  // 所以 module.exports = {...} 这种整体替换能生效。
}
```

> 💡 **循环依赖**：A 引 B，B 又引 A。Node 的解决方案就是上面那行——先把"未完成的 module.exports"放缓存，循环回来时拿到的是当前已导出的部分。

## 🐛 常见错误

| 现象 | 原因 |
|---|---|
| `require is not defined` in ESM | ESM 没有 require，用 `createRequire` |
| `__dirname is not defined` | ESM 用 `import.meta.url` + `fileURLToPath` |
| 发包后 import 不到子路径 | `exports` 字段没加 `"./xx"` |
| 循环依赖结果是 undefined | 重构或推迟取值 |
| pnpm 找不到依赖 | 没声明就直接用是不行的（严格模式） |
