## 一、MRO 是什么

**MRO（Method Resolution Order，方法解析顺序）** 是 Python 为每个类计算出的**唯一线性列表**，列出「查找属性/方法时依次访问的类」。

- 任何类的 MRO 都以自己开头、以 `object` 结尾。
- 查找 `obj.attr` 时沿 MRO 逐个类查，命中即停。
- `super()` 返回的不是「父类」，而是 **MRO 中当前类的下一个类**的代理。
- MRO 在**类定义时**就算好并缓存在类对象上（`cls.__mro__`），运行时不再重算。

对 `class D(B, C)`，MRO 要同时满足三条约束：

| 约束 | 含义 |
|---|---|
| **子类先于父类** | 任何类都必须排在其所有祖先之前 |
| **声明顺序** | 多个直接父类按 `class D(B, C)` 里的书写顺序排列 |
| **单调性** | 某类在父类 MRO 中的相对次序，不能在子类 MRO 中被颠倒 |

前两条是直觉要求，第三条是 C3 特有的——它防止「祖先越过其后代」这类错误。

## 二、C3 公式

记 `L[C]` 为类 `C` 的 MRO，`b1, …, bn` 为 `C` 的直接父类（按声明顺序）：

```
L[object] = [object]

L[C] = [C] + merge( L[b1], L[b2], …, L[bn], [b1, b2, …, bn] )
```

拆开看：

- `[C]` —— 自己永远排第一。
- `L[bi]` —— 每个直接父类**已经算好的完整 MRO**（递归求解）。
- `[b1, …, bn]` —— 直接父类按声明顺序组成的列表；它作为 merge 的最后一个参数，把「声明顺序」压进结果。

## 三、merge 的规则

`merge(seq1, seq2, …, seqk)` 反复执行以下步骤，直到所有序列为空：

1. 取每个序列的**第一个元素**作为候选头。
2. 若某个候选头**不出现在任何其他序列的尾部**（即除它自己所在位置以外的位置），则：
   - 把它追加到结果末尾；
   - 从所有序列中删除该元素。
3. 若某一轮**所有候选头都无法取出**（每个都卡在别人的尾部），则 **merge 失败**，抛 `TypeError`。

「尾部」= 序列中除第一个元素以外的部分。这条检查就是**单调性**的机械实现：一个类若出现在别人的尾部，说明它必须等前面那些类先出队。

## 四、手算示例

### 例 1：经典菱形

```
        A
       / \
      B   C
       \ /
        D          class D(B, C)
```

先求父类：

```
L[A] = [A, object]
L[B] = [B, A, object]
L[C] = [C, A, object]
```

求 `L[D]`：

```
L[D] = [D] + merge( [B,A,obj], [C,A,obj], [B,C] )
```

| 轮次 | 候选头 | 检查 | 取出 |
|---|---|---|---|
| 1 | B, C, B | B 不在任何尾部 | **B** |
| 2 | A, C, C | A 在 `[C,A,obj]` 尾部 → 跳过；C 可行 | **C** |
| 3 | A, A | A 不在任何尾部 | **A** |
| 4 | obj, obj | 可取 | **obj** |

```
L[D] = [D, B, C, A, object]
```

第 2 轮是关键：`A` 虽排在第一个列表头部，却压在 `C` 的尾部里，被跳过，于是 `C` 先出队——**C3 就这样挡住「祖先越过直接父类」**。

### 例 2：`class E(D, A)`（前面广度优先算错的例子）

```
class A: pass
class B: pass
class C(A, B): pass
class D(C): pass
class E(D, A): pass
```

```
L[C] = [C, A, B, object]
L[D] = [D, C, A, B, object]
L[A] = [A, object]

L[E] = [E] + merge( [D,C,A,B,obj], [A,obj], [D,A] )
```

| 轮次 | 取出 | 理由 |
|---|---|---|
| 1 | **D** | 不在任何尾部 |
| 2 | **C** | 不在任何尾部 |
| 3 | **A** | 此时已无尾部阻挡 |
| 4 | **B** | 不在 `[obj]` 尾部 |
| 5 | **obj** | 可取 |

```
L[E] = [E, D, C, A, B, object]
```

`A` 被安排到 `C` 之后，因为第 2 轮时 `A` 还躺在 `[C,A,B,obj]` 尾部——这正是广度优先会提前取出 `A` 的地方。

### 例 3：无解

```
class A(X, Y): pass
class B(Y, X): pass
class C(A, B): pass      # 类定义时即失败
```

merge 到某一步得到：

```
merge( [X, Y, obj], [Y, X, obj] )
```

- 候选头 `X` 在 `[Y, X, obj]` 尾部 → 不可取
- 候选头 `Y` 在 `[X, Y, obj]` 尾部 → 不可取

无候选 → 抛 `TypeError: Cannot create a consistent method resolution order (MRO) for bases X, Y`。失败发生在**类定义阶段**，不是运行时。

## 五、公式与三条约束的对应

| 约束 | 在公式中的位置 |
|---|---|
| 子类先于父类 | 每步 `[C] + merge(...)`，`C` 永远在最前；父类只能从 `L[bi]` 里出队 |
| 声明顺序 | merge 的最后一个参数就是 `[b1, …, bn]`，按书写顺序压着 |
| 单调性 | merge 中「头部不能出现在任何其他序列尾部」的检查 |

## 六、复杂度与实用结论

- 朴素实现 `O(N³)`，CPython 优化到 `O(N²)` 量级；`N` 是继承层次里的类数量。
- **性能从来不是问题，设计才是**。真正该避免的是「菱形 + 各级都实现同名方法」这类需要人脑跑 MRO 的结构。
- 实用建议：多继承尽量做成**混入（mixin）**——只提供正交的一小块能力、不定义 `__init__`、链式 `super().__init__()`；优先用组合而非继承。

## 一句话

> **MRO 是 C3 算出的线性顺序；C3 就是 `L[C] = [C] + merge(各父类 MRO, 父类声明顺序表)`，merge 每轮只取「不在任何其他列表尾部」的头部。** 三条约束由公式结构直接保证；无候选则拒绝建类。
